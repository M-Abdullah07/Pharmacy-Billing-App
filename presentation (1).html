Section A

Project Introduction

PharmaX is a desktop-based, centralised application for Pakistani pharmaceutical wholesale distributors. It replaces fragmented spreadsheets, paper registers, and disconnected billing software with a single integrated platform.

🎯 Problem

Manual processes cause billing errors, stock discrepancies, compliance violations, and lost revenue across Pakistan's pharmaceutical supply chain.

💡 Solution

Fully integrated platform covering master data, inventory, purchase/sales, financial ledgering, and data export — with DRAP & FBR compliance built in.

Tech Stack

  • Desktop: Electron + Vite
  • Frontend: React + Tailwind CSS + shadcn/ui
  • Backend: Node.js IPC Services
  • Database: PostgreSQL 16
  • Security: Argon2id password hashing

Target Users

Medium to large pharmaceutical wholesale distributors operating across Pakistan — enabling accuracy, speed, and regulatory confidence.

Section B

Advantages & Constraints

✅ Advantages

DRAP & FBR Compliance: Batch-level MRP tracking, drug schedule classification, GST-compliant invoicing with FBR slabs.

FEFO Batch Allocation: Automatic First-Expiry-First-Out selection during sales prevents expired stock from being sold.

Real-Time Intelligence: Live dashboard with KPIs, near-expiry alerts, activity feed, and analytics charts.

Offline-First Desktop: No internet dependency — runs locally with PostgreSQL. Data never leaves the pharmacy.

Modular Architecture: Service-per-domain backend (8 services) enables parallel development and easy maintenance.

⚠️ Constraints

PostgreSQL Dependency: Requires separate database installation — adds setup complexity for non-technical users.

Electron Bundle Size: ~200MB app size due to Chromium engine bundled with Electron.

Single Workstation: Currently designed for single-machine use. Multi-terminal/network deployment is not yet supported.

No Cloud Sync: Backup is manual (JSON/CSV export). No automated cloud backup or multi-site replication.

Limited Role System: Currently single admin role. Multi-role RBAC (cashier, manager) is deferred to future release.

Section C

Non-Functional Requirements

NFR-1: Performance

The system must load stock views and ledger screens within 2 seconds for datasets up to 20,000 batch records and 5,000 transactions.

MetricTarget
Dashboard KPI load< 1.5 seconds (parallel queries)
Stock summary (20k batches)< 2 seconds
Supplier ledger (5k records)< 2 seconds
Sale invoice creation (FEFO)< 3 seconds with lock + commit

Achieved via: PostgreSQL indexing, parallel Promise.all() queries, lazy pool initialization.

NFR-2: Security

The system must protect against unauthorized access and SQL injection. All passwords must be hashed with Argon2id.

ControlImplementation
Password hashingArgon2id (memory-hard)
Account lockout5 failed attempts → 15 min lock
SQL injection preventionParameterized queries + allow-list
Process isolationcontextBridge + contextIsolation

Achieved via: Electron contextIsolation, preload bridge, removed open query handler.

Section H

Lessons Learnt

1
Requirements change — iterate. Purchase Returns emerged mid-sprint; Agile saved us.
2
Monoliths collapse — modularize. 1,500-line main.js refactored to 8 SOLID services.
3
Schema first, UI second. Every hour on ERD saved days of debugging.
4
Never trust user input. Found real SQL injection; fixed with allow-lists.
5
Tech choices have trade-offs. PostgreSQL power vs. installation complexity.
6
Test at the boundaries. BVA caught real edge cases in login & signup.
7
Git is a team survival tool. Lost work early; learned to commit often.
8
Docs are deliverables. Essential for onboarding and decision tracking.
9
UX is engineering. Splash screen prevented users thinking app crashed.
10
Track debt, don't ignore it. Shipped on time with a clear audit backlog.
