## P1 — Financial correctness — ✅ all (2026-07-05)

| Item | Status | Notes |
|---|---|---|
| H2 — customer-payment FIFO locking | ✅ | `record-customer-payment` (ledgerService.js) now takes `FOR UPDATE` on the candidate `sale_invoices` rows before allocating, inside the existing transaction. Prevents two concurrent payments from reading the same `balance_due` and double-allocating. |
| M1 — supplier payment FIFO allocation | ✅ | `purchase_invoices` had no `amount_paid`/`balance_due` — added both via migration `v3.1.0_financial_correctness.sql` (mirrors `sale_invoices`, `balance_due` is a GENERATED column, backfill is a no-op since no `payments WHERE direction='paid'` existed pre-migration). `record-supplier-payment` now FIFO-allocates with the same `FOR UPDATE` pattern as H2. |
| M7/M8 — isCredit + credit_limit | ✅ | `add-sale` now rejects any `data.isCredit` that isn't strictly `boolean`. For credit sales, the customer row is locked (`FOR UPDATE`) and outstanding (`opening_balance + SUM(balance_due)` over confirmed invoices) is compared against `credit_limit`, rejecting if it would be exceeded. **Conservative choice (needs sign-off):** `credit_limit = 0` is treated as "unlimited" — matching the existing DB trigger `fn_check_credit_limit`'s own convention (`IF v_credit_limit > 0 THEN check`). Schema default for `credit_limit` is `0.00 NOT NULL`, so this is the only convention already live in production; a stricter reading (0 = zero credit allowed) would contradict the trigger that's already running and would need explicit product sign-off to diverge. |
| H14/H15 — field-name mismatches | ✅ | Found and fixed exactly two: `Frontend/src/pages/AddCustomers.jsx` and `Frontend/src/pages/Companies.jsx` both read `result.lastID` off `addCustomer`/`addSupplier` responses, but those handlers (`partyService.js`) return `{success, customerId}` / `{success, supplierId}` — never `lastID`. `lastID` was always `undefined`, so new customers/suppliers silently got `entity_id: undefined` on any pending contact-person rows added in the same flow. A full agent-assisted sweep of every other add/create IPC round-trip (purchase invoices, purchase returns, batches, contacts, products, sales, auth) found no further mismatches — all other call sites already read the correct field name. **Unrelated dead-feature bug spotted in passing (not fixed, flagged only):** `Frontend/src/pages/AddArea.jsx` calls `window.electronAPI.addArea(...)`, but `Backend/app/preload.js` documents that `addArea`/`getAreas` were intentionally removed — this call always throws. Out of scope for a field-name-mismatch fix since there's no handler at all. |
| M30 — ledger opening balance | ✅ | `get-customer-ledger` / `get-supplier-ledger` now return `{ openingBalance, entries }` instead of a bare array (smallest-diff option was extending the two existing consumers rather than adding parallel handlers). `openingBalance` = the party's `opening_balance` column + all debits/credits dated before `startDate` (0 if no `startDate` given, i.e. just the onboarding balance). Both consumers (`Frontend/src/pages/CreditDues.jsx`, `Frontend/src/pages/SupplierLedger.jsx`) updated: `calculateRunningBalance` now seeds from `openingBalance` instead of 0, and an "Opening Balance" row renders above the ledger table when non-zero. Defensive fallback kept for the old bare-array shape. |
| C4/H7 — v_customer_ar / v_supplier_ap fan-out | ✅ | Both views previously `LEFT JOIN`ed invoices AND payments directly onto the party in one query, so N invoices × M payments produced N*M rows, inflating every `SUM()`. Rewritten with `invoice_agg`/`payment_agg` CTEs pre-aggregated per party before joining — no more fan-out. Applied via migration + live DB + `pharmax_schema.sql`. |
| M18 — AR ageing buckets | ✅ | The bucket `FILTER` clauses were already correctly per-invoice (aged by each invoice's own `due_date` relative to `CURRENT_DATE`), not lumped by customer — the bug was purely the fan-out corrupting the sums, which C4/H7 fixes. No separate bucket-logic rebase was needed once fan-out was removed; verified with an isolated test (`Backend/tests/integration_p1_financial.js`) that reconstructs the exact query and checks exact expected sums. |
| C4/H7 (analytics) — get-analytics-chart-data fan-out | ✅ | Same fan-out shape in `systemService.js`: `sale_invoices` and `purchase_invoices` were both `LEFT JOIN`ed to the same `months` row, so a month with N sales and M purchases produced N*M rows. Fixed with `monthly_sales`/`monthly_purchases` pre-aggregation CTEs joined onto the month series. |
| H8/H9 — opening_balance immutability + header totals | ✅ | `confirm-purchase-invoice` and `add-purchase-return` (`purchaseService.js`) both mutated `suppliers.opening_balance` — removed both mutations; `v_supplier_ap` already derives outstanding payable from `opening_balance + SUM(confirmed net_payable) - SUM(payments)`, so the mutation was double-counting every confirmed invoice. `confirm-purchase-invoice` now also recomputes `subtotal`/`discount_amount`/`tax_amount`/`net_payable` server-side from `purchase_invoice_items` instead of trusting whatever the frontend sent at `add-purchase-invoice` time. **Flagged, not fixed (out of scope for H8/H9):** neither `v_customer_ar` nor `v_supplier_ap` nets `sale_returns.total_credit` / `purchase_returns.total_credit` against the outstanding balance — a pre-existing symmetric gap on both sides that predates this session and would need its own view change beyond the fan-out/ageing scope of C4/H7/M18. |
| H1/M15/M16 — schema drift & migrations | ✅ | `database/pharmax_schema.sql`'s `v_stock_summary` had drifted from the live DB: the file had `LEFT JOIN suppliers s ON s.supplier_id = p.manufacturer_id` with `is_imported` hardcoded `FALSE`; live DB has `JOIN manufacturers m ON m.manufacturer_id = p.manufacturer_id` with `is_imported` correctly derived from `m.country <> 'Pakistan'`. Schema file corrected to match live truth (captured via `pg_get_viewdef`). Also found and fixed a **sequence-backfill bug** in `database/migrations/v3.0.1_race_condition_hardening.sql`: `regexp_replace(invoice_number, '\D', '', 'g')` strips ALL non-digits including the year, so `'INV-2026-000012'` backfilled as `2026000012` instead of `12` — fixed to extract only the segment after the last `-`. **Not re-applied live**: the live sequence (`sale_invoice_num_seq` = 16) is already correct and ahead of `MAX(12)`; re-running the corrected `setval` expression now would move it backward to 13, which would cause duplicate-key failures on the next sale. The fix only protects future/fresh deployments of this migration file. products→manufacturers vs batches/purchases→suppliers is the intended FK design, not drift — left untouched per instructions (no FK restructuring). |

New migration: `database/migrations/v3.1.0_financial_correctness.sql` (idempotent — verified by running it twice against the live DB with no errors and no duplicate side effects). ## Proposed, not approved (owner sign-off needed)
- **Minimum shelf-life setting:** C1 now allows selling a batch that expires *today* (consistent with stock display). Pharmacies often refuse to dispense stock expiring within N days/months. A configurable "minimum remaining shelf life" would be a day-one customer request.
- **`get-batches-by-product` display drift:** `stockService.js` `get-batches-by-product` shows batches with no expiry/quantity filter while `get-stock-by-product` filters both. Not touched (out of P0 scope) — should be reconciled deliberately, probably in P3 consolidation.
- **Expired-stock disposal flow:** with C1 fixed, expired stock now sits invisible to sales forever. There is no write-off/disposal movement type surfaced in the UI. Regulatory expectation for pharmacies; propose for the feature roadmap.
