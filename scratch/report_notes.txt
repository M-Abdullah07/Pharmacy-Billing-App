1. Project Introduction
PharmaX is a desktop-based, centralised application engineered for Pakistani pharmaceutical wholesale distributors. It eliminates reliance on fragmented tools — spreadsheets, paper registers, and disconnected billing software — by providing a fully integrated platform for master data management, inventory tracking, purchase and sales processing, financial ledgering, and data export, all within a single, role-based desktop application.
The system is designed in compliance with Pakistan's pharmaceutical regulatory framework: DRAP (Drug Regulatory Authority of Pakistan) for drug scheduling and batch-level tracking, and FBR (Federal Board of Revenue) for GST-compliant invoicing. Key Pakistan-specific features include STRN/NTN identification for suppliers and customers, DRAP drug schedule classification (OTC / G / H / H1 / X), batch-level MRP as mandated by DRAP, and support for local payment modes including JazzCash and EasyPaisa.
Target users are medium to large pharmaceutical wholesale and distribution businesses operating across Pakistan. The system is designed to reduce compliance exposure, eliminate manual reconciliation, and provide real-time visibility into stock, receivables, and payables — enabling distributors to operate with greater accuracy, speed, and regulatory confidence.

US-301 — Dashboard Live KPI Panel

UC-301

Actor(s)

Alt Flow(s)
Alt Flow A — No sales yet: If no confirmed invoices exist, Total Sales and Total Profit display Rs 0 and Out-of-Stock shows the full count of active products with no batches.
Exceptions
E1 — electronAPI unavailable: If the Electron IPC bridge is not initialised, the panel renders a red error banner: 'Dashboard error: electronAPI not available'.E2 — Database query failure: If any query throws, the error is caught and displayed in the error banner; other panels are unaffected.

5. Architecture
5.1 Chosen Architecture Pattern
Pattern: Layered (N-Tier) Architecture with Service Modules + Dependency Injection (CURRENT IMPLEMENTATION)
Justification
Layered architecture naturally separates concerns into presentation, business logic, and data access layers, making the desktop Electron application modular and testable.
Service-oriented design (already implemented) encapsulates business logic into domain-specific modules (authService, productService, saleService, purchaseService, stockService, ledgerService, partyService, systemService), enabling parallel development and easy maintenance.
Dependency Injection pattern used in main.js ensures services receive database context ({ queryDb, runDb, pool }) at initialization, reducing coupling and improving testability.
IPC Handler Registration (Electron-specific) sits in each service module, mapping backend logic directly to frontend-accessible channels without requiring a separate router layer.
ES6 Module System (import/export) provides clean, modern code organization compared to CommonJS.
This pattern enables future expansion: REST API layer can wrap services, database abstraction via repositories can replace direct queries, or role-based access control can be added at handler level without touching core logic.

11. Lessons Learnt
The following lessons were drawn from building PharmaX across three sprints — each grounded in a concrete experience from the project rather than abstract theory.
1. Requirements Engineering & Iterative Development
We learned that requirements are never complete on day one. Our project evolved across three iterations, and each cycle revealed gaps in the original specification. The original design had no concept of Purchase Returns — this requirement emerged only after implementing the Purchase Invoice module, when we realised pharmacies need to send damaged goods back to suppliers. We had to design a new purchase_returns table, its associated backend service, and frontend UI mid-sprint.
Takeaway: Agile iteration is not just theory from textbooks — it genuinely saves projects. Trying to lock down every requirement upfront would have produced a system that does not match real pharmacy workflows.
2. SOLID Principles — Learned the Hard Way
The most impactful technical lesson was understanding why SOLID principles matter, because we experienced the pain of violating them first. Our initial main.js was a single 1,500+ line file containing every database query, every IPC handler, and all application logic. Adding a new feature meant scrolling through thousands of lines and hoping nothing unrelated broke.
We refactored into a service-per-domain architecture — authService, productService, partyService, stockService, purchaseService, saleService, ledgerService, and systemService — each following the Single Responsibility Principle. The main.js now only registers services in a few clean lines.
Takeaway: SOLID is not academic theory — it is the difference between a codebase that grows gracefully and one that becomes unmaintainable within weeks.
3. Database Design & Schema Evolution
Designing a normalised relational schema for a real-world domain — pharmacy inventory with batches, expiry dates, and multi-supplier relationships — taught us that ERD diagrams are essential, not optional. Database triggers and constraints (auto-generating invoice numbers, stock movement tracking) push business logic to where it is most reliable: the database itself. Our migrations folder grew as we added purchase_returns, payments, and expenses tables that were not in the original design.
Takeaway: Spend time on the data model before writing UI code. Every hour invested in schema design saved us days of debugging later.
4. Security — SQL Injection Is Real
We discovered actual SQL injection vulnerabilities in our own production code. An open query-db IPC handler allowed any SQL to be executed from the frontend, and an unvalidated table name was interpolated directly into a query string. We fixed both: the open handler was deleted entirely, and an allow-list was introduced for CSV exports so only pre-approved table names can pass through.
Takeaway: Security is not a feature added at the end — it must be considered from the start. Even in a desktop app with no internet-facing API, the renderer process should never be fully trusted.
5. Architecture Decisions Have Long-Term Consequences
Choosing Electron + React + PostgreSQL gave us a powerful stack, but we learned that architectural decisions made early become expensive to change later. PostgreSQL gave us full relational power and triggers but requires a separate database installation for end users. The IPC-based backend provides process isolation and security but adds verbose boilerplate for every new feature. Every decision involves trade-offs.
Takeaway: There are no free technology choices. Understanding trade-offs is a core software engineering skill.
6. Testing — Not Just Writing Tests, but Thinking in Boundaries
Applying Boundary Value Analysis and Equivalence Class Partitioning from our SE lectures to actual code made the concepts tangible. The password minimum length boundary (5→6→7 chars) caught a real edge case in our signup validation. The account lockout boundary (4→5 failed attempts) verified our security mechanism works at the exact threshold. Empty and whitespace input boundaries revealed that .trim() was critical for username validation.
Takeaway: Testing theory from lectures becomes meaningful only when applied to your own code — discovering bugs you would otherwise have shipped to users.
7. Version Control & Collaboration
Working as a team on a shared codebase taught us to commit early and commit often — we lost work early on due to uncommitted changes. Branching matters: the test branch alongside main showed how feature branches prevent destabilising production code. Merge conflicts are normal, not errors, and resolving them is a skill that only improves with practice.
8. Documentation Is a First-Class Deliverable
Our project produced multiple documentation artefacts — UML diagrams, architecture documentation, sprint user stories, and a code audit — that were not afterthoughts. They were essential for onboarding team members to modules they did not write, for tracking design decisions (e.g. why FEFO was chosen for batch allocation), and for connecting code to SE concepts in course deliverables.
Takeaway: Code without documentation is a liability. Documentation without code is fiction. You need both, kept in sync.
9. UI/UX Matters More Than We Expected
Even a backend-heavy pharmacy management system lives or dies by its interface. The splash screen was not cosmetic — without it, users thought the app had crashed during the 2–3 second database initialisation. Toast notifications for success and error feedback prevented users from double-submitting invoices. Professional design with proper spacing and iconography increased trust from test users compared to the raw HTML prototype.
Takeaway: Software engineering is not just about making things work — it is about making things work for people.
10. Technical Debt Is Inevitable — Managing It Is the Skill
By the end of the project we had accumulated identifiable technical debt: components exceeding 1,000 lines that need splitting, duplicated toast logic across 8+ files, missing React Error Boundaries, and no server-side input validation on IPC handlers. We tracked this in a code_audit.md file with severity ratings and a prioritised backlog.
Takeaway: Shipping imperfect code on time while maintaining a clear record of what needs improvement is more professional than endlessly refactoring and never delivering.
